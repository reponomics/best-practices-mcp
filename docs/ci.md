# Continuous integration and repository setup

The workflows maintain the bounded eleven-tool MCP; they do not add runtime services or automate BadgeApp submission. Development and security tools are not required to run an installed server. Release management and publication are described in [the release procedure](releasing.md).

## Checks and scope

| Workflow | Trigger and coverage | Required setup |
| --- | --- | --- |
| Compatibility and coverage | Pull requests to `main`, pushes to `main`, and manual runs; Python 3.11/3.12 on Ubuntu, macOS and Windows, offline regression/coverage, catalog checks and fresh wheel/sdist installation | GitHub Actions; development-only Node is selected from `.nvmrc` (24.22.3) |
| Actionlint | PRs/pushes to `main` and manual runs, including documentation-only changes; all workflow YAML files | Read-only job, sparse checkout, fork v1.17.1 built with Go 1.27.4; no secrets or publication credentials |
| Semantic PR | PR title metadata for PRs targeting `main`; conventional type/title validation | Squash-only merges and PR-title squash defaults make the validated title the commit on `main` |
| Upstream criteria update | Monday 09:23 UTC and manual runs on `main`; refreshes retained upstream sources, catalog and documentation pins in one regular PR; deletes the reserved branch after merge | Existing Release App credentials for signed commits/PR events; optional `UPSTREAM_UPDATES_PAUSED=true` pauses updates for manual fixes |
| OSV dependency scan | PRs/pushes to `main`, weekly schedule and manual runs; separate vulnerability and license checks of the Python/npm locks and a CI-generated actionlint module inventory | Public OSV, deps.dev and Go module service access; no credential is needed for the scans |
| CodeQL | PRs/pushes to `main`, weekly schedule and manual runs; Python, JavaScript/TypeScript development code and GitHub Actions | Advanced setup in the new repository; public repository or licensed private code scanning |
| Coverage upload | Called after the existing compatibility matrix; uploads its Ubuntu/Python 3.11 report without rerunning tests | Codecov repository connection and `CODECOV_ENABLED=true` |
| Scorecard supply-chain review | Public default-branch pushes, branch-protection changes, weekly schedule and manual runs | Public `reponomics/best-practices-mcp`; results are review guidance, not an arbitrary score threshold |
| Release Please / PyPI | Release PR management, draft/tag preparation, tagged candidate dispatch, release-time scans/SBOMs, approved attestation/PyPI publication, then immutable GitHub asset publication | Release App and PyPI OIDC/environment setup; see [releasing](releasing.md) |

The six compatibility jobs retain their own measured coverage and installation evidence. Their environment reports also record the invoked GNU Make version (`make`), or `unavailable` if it cannot be determined; this is provenance information, outside the current OSV scan scope. Codecov shows server coverage trends from one representative matrix job; it does not replace the Windows/macOS results or imply combined multi-platform coverage. Its project and patch percentage statuses are informational. Tests and report-generation failures remain failures; no percentage threshold is substituted for the behavioral contract.

## Workflow linting

The separate `.github/workflows/actionlint.yml` workflow runs with only `contents: read` on an ephemeral Ubuntu runner. It uses a depth-one, non-cone sparse checkout limited to `.github/workflows/*`, with checkout credentials disabled. It checks every workflow YAML file even for documentation-only changes. The compatibility test matrix also continues to run for those changes.

This is a tentative adoption of kjanat/actionlint v1.17.1, pinned to commit `220b76cfa568e00ed8b3c476898f849a722b88e2` and built from source with Go 1.27.4. A separate shallow checkout supplies the pinned fork source; the workflow verifies that revision and builds only `cmd/actionlint`. It does not install this Python project or run contributor tests. It passes explicit project workflow paths to the linter so the fork's own workflows are not included. ShellCheck and Pyflakes integrations are disabled in this dedicated job so it does not invoke incidental runner-installed tools; local actionlint may use those optional tools when available. The temporary source build avoids using the release binaries built with the older Go toolchain. Reassess this selection before adopting a new release; the fork's development branch describes a substantially changed v2.

The lint step captures structured JSON and stderr rather than printing raw diagnostics as runner commands. An inline reporter validates file locations and escapes annotation text and properties, shows a bounded set of file-and-line annotations, and writes a summary containing trusted counts and status. The complete reports are retained for 14 days even when linting fails. Lint findings, tool failures and malformed reports fail the check after reporting. The job has no PR-comment API, SARIF upload, write permissions or publication credentials, and its reports are not inputs to a privileged release job. No separate privileged reporting workflow is needed.

## Dependency inventory

`uv.lock` is the universal development lockfile for runtime dependencies, the installed `dev` group and the non-default `audit-tools`, `inventory-tools` and `release-tools` groups. Local setup, compatibility CI and release qualification all use `make setup` to synchronize locked dependencies into `.venv` by default (the compatibility matrix overrides `VENV` as described below). `.python-version` defaults to Python 3.11; CI overrides `BOOTSTRAP_PYTHON` for its 3.11/3.12 matrix. `package-lock.json` covers development-only DOM tooling. The minimum supported Node version is 24.22.3 within the 24.x line; `.nvmrc` selects the exact version for nvm, compatibility CI and release qualification. See [ADR 0002](adr/0002-development-toolchain.md) for the decision and alternatives.

uv is an external bootstrap tool. Its exact requirement lives in `[tool.uv].required-version`; `setup-uv` reads this from `pyproject.toml`. The matching distribution is locked in `audit-tools` solely for inventory and is excluded from normal setup. `make tooling-check` checks agreement between these declarations and `uv.lock`; `.tool-versions` and asdf are not used. pip remains a locked development dependency for offline package checks. The CI-only `inventory-tools` group reuses the locked PyYAML parser; CI installs only this group into a separate environment without installing the project. Release evidence uses a separate `release-tools` environment for pinned CycloneDX Python; the generator inspects fresh runtime environments without being installed in them.

OSV scans both committed lockfiles and the generated actionlint inventory explicitly with implicit resolution disabled, including the uv audit entry. This inventories declared package versions rather than attesting to installed bootstrap binaries or every OS tool. Scanner failures remain failures, and reports are retained when produced. Fresh-consumer checks install wheels and sdists through pip in clean environments without the development lock, so their transitive versions can differ from the scanned inventory.

Before scanning, CI reads the kjanat/actionlint hook's full SHA and Go version from `.pre-commit-config.yaml` and checks agreement with the source and toolchain pins in `.github/workflows/actionlint.yml`. With that exact Go toolchain, `scripts/actionlint_inventory.py` resolves the SHA through Go's module service, verifies the returned source hash, repository and release version, and reads both the release's module graph and the imports of `./cmd/actionlint` using read-only `go list` commands. The generator checks that the upstream `go.mod` and `go.sum` bytes remain unchanged and rejects unresolved or replaced modules. It downloads source/module metadata but does not build or execute actionlint. Generation failures fail the job and cannot reuse a stale inventory.

The module inventory includes actionlint itself and the union of modules imported by `./cmd/actionlint` across Linux, macOS and Windows on amd64 and arm64, with cgo enabled and disabled. Upstream maintenance/test-only modules are excluded from that executable inventory; the complete module graph is retained separately. A separate `stdlib-inventory.json` records the pinned Go standard-library version for vulnerability scanning only; the module license check does not query the synthetic `stdlib` package as a separately distributed dependency. These are version-based checks, not live reachability analysis or an attestation of contributors' compiled binaries.

Under `build/actionlint-inventory/`, CI writes `inventory.json`, `stdlib-inventory.json`, `full-graph.json`, `imports.json`, `provenance.json` and upstream `go.mod`/`go.sum`. Provenance records the source SHA, resolved version, Go version, target configurations, module checksums and input hashes. Both OSV report artifacts retain these files even when a scanner fails before producing its report. Nothing in that directory is committed or included in the Python distributions, and normal contributor setup and pre-commit checks do not generate it or require a separate Go installation.

The OSV job also enforces the dependency license allowlist, including BlueOak-1.0.0 and 0BSD, using version-specific metadata corrections and the documented Docutils development-tool exception in `osv-scanner.toml`. These entries do not suppress vulnerabilities. Both scans explicitly load that root policy, including for the generated Go packages. There is no actionlint advisory exception or generated suppression policy. The fork fixes the former x/sys finding, and the pinned Go 1.27.4 build avoids the older Go version in the published v1.17.1 binaries. Newly exposed findings require investigation, not automatic exclusions.

Reassess license corrections and exceptions when a package's version or use changes, and keep the workflow's allowlist and the Makefile's `OSV_LICENSES` value together when changing policy. Both scan steps fail on findings or scanner errors, and the license step runs even after an earlier failure. Vulnerability SARIF stays in `osv-dependency-report`; license results, policy and lockfiles are retained separately in `osv-license-report` for 14 days. OSV 2.7.1 omits license findings from SARIF, so inspect the license JSON artifact for those findings. Contributors may rely on the PR workflow rather than installing the scanner locally; see the [dependency policy](../CONTRIBUTING.md#dependencies).

All six compatibility jobs invoke the canonical Make targets for setup, quality, lock/catalog checks, coverage, offline wheel checks and fresh-consumer installation. Windows invokes native GNU Make 4.4.1 from PowerShell; the Makefile selects `cmd.exe` recipes. Every matrix job uses `build/dev venv` to exercise paths containing spaces. Help is tested before environment creation. Release qualification also uses Make, while its publishing job retains its separate trust boundary. Release scans additionally cover the actual dependency resolution in each qualified installation, and publication requires those scans to pass. Runtime-reference SBOMs, tooling inventory, SARIF, license JSON, hashes and signed provenance become immutable release assets; see the [release procedure](releasing.md).

Use `make lock` to regenerate the lock and `make lock-check` to verify it. For a uv update, change both the executable requirement and the audit-group pin, install the new external version, regenerate the lock, and rerun setup and checks.

Review the lock diff and rerun the required checks when accepting dependency updates. Dependabot proposes weekly grouped Python/uv, npm and GitHub Actions updates, plus pre-commit hook updates, with conventional PR-title prefixes. Its native pre-commit integration maintains actionlint’s release SHA and `# frozen:` version comment together. Each actionlint pin update regenerates the inventory in its PR workflow. Update the lint workflow’s source SHA and release version alongside the hook; update both workflows’ Go version and the hook’s `language_version` together. Inventory generation rejects inconsistent pins. Dependabot’s pre-commit ecosystem provides version updates, not security updates or vulnerability alerts; the separate OSV scans check the derived Go module inventory. Major Python/npm updates remain separate for deliberate compatibility review; grouped security updates remain reviewable and do not auto-merge. Dependabot configuration does not itself enable repository vulnerability alerts or security-update settings; enable those in the new repository.

## Code scanning

This repository contains an explicit advanced CodeQL workflow. Do not enable GitHub's default CodeQL setup alongside it. The workflow scans interpreted source without installing or executing the project. Code scanning activates automatically when the target repository is public. While private, set `PRIVATE_CODE_SCANNING_ENABLED=true` only after enabling the necessary GitHub Code Security entitlement. Before that, the CodeQL job is visibly skipped, not qualified as a successful analysis.

OSV vulnerability scanning runs independently of code-scanning availability. Its SARIF upload requires the target repository to be public or explicitly enabled for private code scanning, and is omitted for fork PRs whose tokens cannot upload it. The downloadable report and scan exit status remain available. Do not waive vulnerabilities merely to make publication green; investigate and record any narrowly justified exception explicitly rather than copying another project's overrides.

## Codecov setup and privilege boundary

Install or authorize the Codecov GitHub App for `reponomics/best-practices-mcp`, connect the repository, then set repository variable `CODECOV_ENABLED=true`. This is a service integration, not a PyPI publishing credential. No stored Codecov token is configured. The upload job uses GitHub OIDC for same-repository events. Public fork PRs use Codecov's tokenless fork path and receive no OIDC token; private fork uploads are skipped.

Coverage measurement runs in the ordinary read-only compatibility jobs. A separate upload job downloads the current run's named coverage artifact and reads checked-out paths solely for mapping; it does not install or execute project code. It has only the additional `id-token: write` permission needed by Codecov. An enabled upload that fails fails its job, while its coverage percentage statuses remain informational. Verify the first actual upload and commit/path mapping before relying on the dashboard.

## Repository controls and activation

Keep workflow-level permissions read-only. Additional token permissions are declared only on the jobs that need them. Actions are pinned to reviewed full commit SHAs; Dependabot maintains those references. The semantic-title workflow reads PR metadata without checking out PR code. Upstream patch preparation runs trusted code from `main` with read-only permissions; a short-lived App token then publishes only the allowlisted source/catalog/documentation files. Its single concurrency group serializes updates and branch cleanup. The merge cleanup job has `contents: write` solely to remove the reserved branch when its head still matches the merged PR. See the [upstream update procedure](upstream-compatibility.md#checking-for-upstream-changes) for branch ownership and pausing updates. Release App secrets and publication OIDC are never available to ordinary test jobs. The release dispatcher has only the extra Actions permission needed to start the tagged workflow. Metadata-only draft preflight and final GitHub asset publication have Contents write permission; the approved PyPI job has OIDC and Attestations write permission. None of those privileged jobs checks out or executes project build code.

Before public release, configure the `main` ruleset to require the six compatibility jobs, semantic PR title check and OSV scan. Require `Check workflow files` as well; its first hosted run succeeded on the pinned fork. After the first successful CodeQL run, add its three analysis checks where supported. Require PRs, verified signed commits on main and squash-only merges, with the PR title used as the squash commit title. Enable immutable GitHub releases before the first release; Release Please uses lightweight tags pointing to the signed release commits, not separately signed annotated tags. Do not require release/publication jobs or scheduled Scorecard analysis on ordinary PRs. Codecov percentage statuses remain informational. The exact check names should be selected from successful runs in the new repository rather than guessed from an old repository's check inventory.

The pre-release repository starts private and becomes public immediately before the first release. At that checkpoint, verify the environment approval gate, activate applicable code scanning, run the required checks in the new repository, and inspect any pending/skipped integrations honestly. A workflow file or a skipped job does not establish that CodeQL, Codecov, OSV or publication has succeeded. Public-service activation and the first real results are distinct from local YAML/actionlint and configuration validation.

## First push to exercise CI

Create the private `reponomics/best-practices-mcp` repository without a generated README or license, connect its remote, and push the reviewed `main` history. Use conventional-title pull requests for subsequent changes and inspect checks against the exact commits being reviewed.

Keep `PYPI_PUBLISH_ENABLED` unset and leave the release App variable unset while bringing up ordinary CI. The compatibility matrix and OSV scan can run before publication setup. A private-repository CodeQL skip is expected until the required entitlement or public visibility is in place; Codecov remains skipped until explicitly connected. Review actual run results before selecting required checks, then use the signed squash path for approved pull requests. Configure release services separately using the release procedure. No live browser session is needed for this first push; the first published beta must pass the browser runbook before stable promotion.

## Local validation

`make validate` runs lock consistency, quality checks, offline tests, catalog reproduction and workflow lint in one command. It continues with independent checks after failures and returns a failing status if any check fails; workflow lint uses the pinned fork’s actionlint pre-commit hook, with its environment installed and cached on first use. See [contributor prerequisites](../CONTRIBUTING.md#validate-the-implementation). OSV runs in CI and is not part of standard contributor validation. Maintainers and contributors who want proactive checks can follow the [optional local scan instructions](../CONTRIBUTING.md#optional-local-dependency-scans). `make check` remains the offline regression/lint interface, and `make test-coverage` measures server coverage locally. CodeQL/Codecov/Scorecard are qualified through their configured GitHub jobs; local configuration checks do not substitute for those executions.
