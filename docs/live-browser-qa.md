# Local live browser QA

Exercise the installed candidate before promoting a beta to stable, and repeat for subsequent release candidates. Use [MCP Inspector](inspector-qa.md) connected to the exact installed candidate, an authenticated Chrome session, and the [PolicyChecks silver form](https://www.bestpractices.dev/en/projects/14356/silver/edit). This is a short supervised integration check, not an automated production save. Discard the previews when finished.

## Preparation

Follow the [published-package checks](releasing.md#verify-the-published-beta-and-advance-to-stable) first. Start with the setup and offline catalog/document checks in [Inspector qualification](inspector-qa.md); the live-browser matrix below completes its proposal-application checks. Record the server version, distribution identity, Inspector/Node versions, OS, browser and date in `INTERNAL/live-qa/<version>/`. Keep generated tool arguments/results, exact URLs and screenshots there; do not capture credentials or authentication cookies. The existing [Chrome record](live-qa/2026-11-09/README.md) illustrates useful evidence but does not replace a fresh check.

Through Inspector, call `get_project_progress` with `{"project_id":14356,"level":"silver"}` and `get_criteria` with `{"level":"silver"}`. Verify the returned project is `reponomics/PolicyChecks`. Open the plain edit page and record the actual starting values with screenshots of every selected case, including neighboring controls. Public JSON is not a substitute for this browser baseline. If page automation changes a value relative to the public response, choose another field for that condition or record the discrepancy and investigate. The MCP does not predict form state; the table below derives browser checks from upstream's documented proposal procedures and the actual baseline.

Choose distinct silver criteria with the baseline conditions below, using canonical field names returned by `get_criteria`. Selection is deliberate because a project's answers change over time. Possible candidates include `contribution_requirements`, `crypto_weaknesses`, `external_dependencies`, `dco` and `documentation_architecture`; inspect their current states before assigning roles. If a required condition is unavailable, mark that case unexercised and select another authorized application before claiming complete coverage.

| Role | Baseline and supplied fields | Browser check after opening URL A |
| --- | --- | --- |
| A: blocked pair | Existing known status; propose a different known status and new justification; override only the justification | Existing status and justification retained; justification is blocked by the unforced differing status |
| B: status override | Existing known status and nonblank justification; supply the same status and new justification; override the status | Both fields remain in the URL. BadgeApp retains the same status and replaces the justification through its documented status-override implication |
| C: blank pair | Blank or unknown status and blank justification; supply `Unmet` and new justification, no override | Both supplied values fill |
| D: retained wording | Existing nonblank justification; supply different text without a status or override | Existing wording retained |
| E: clear wording | Existing nonblank justification; supply an empty string and override that justification | Justification cleared |
| F: matching values | Supply a known status and justification exactly equal to their current values, without overrides | Both fields remain in the URL; displayed values stay the same |

Use unmistakable preview text, for example the exact string `  QA preview only — not saved. https://github.com/reponomics/PolicyChecks?q=a&x=2#qa  `, for each new nonempty justification. Explain this test text before opening previews: the `?q=a&x=2#qa` fragment is deliberately part of a justification URL, not a leaked proposal parameter. It should appear only in fields where the proposal applies and should disappear when the preview is discarded. This combines Unicode, URL punctuation, and leading/trailing ASCII spaces. The six roles supply at least ten fields in the same artifact. Additional silver standalone justifications may be included with explicit overrides. They are temporary test values, not criterion assessments.

## 1. Two combined proposal URLs

Build a flat document using `build_draft` with `draft: {}` and the chosen fields in `changes`; retain its returned `draft`. Call `prepare_update_url` with `project_id: 14356`, `level: "silver"`, that explicit `draft`, and `override_fields` containing A's justification, B's status, E's justification and any explicitly selected additional fields. Substitute actual canonical names; the role letters above are not tool arguments.

Retain the returned field-level `transfer`, `requested_overrides`, `effective_overrides` and exact `artifact.url`. Check that every eligible supplied field is marked `encoded` and represented exactly in the decoded query, including F's matching values and all whitespace. The `overrides` parameter must contain only the explicit requested names; B's justification must not be added automatically. The report must contain no expected-form classifications. Open URL A by clicking a link rendering the exact Inspector-returned URL and compare all selected controls with the table. If Inspector does not render a clickable link, use a local evidence document containing that exact link and record the actual delivery route; do not claim an Inspector link-click check. Verify BadgeApp's documented trimming of leading/trailing spaces in newly applied justification text, while interior text and punctuation survive. Distinguish the exact encoded value from the value displayed by the site. Check untouched neighboring controls as well. An unexpected `artifact: null`, exclusion, or browser result is a finding to resolve, not permission to hand-edit the generated URL.

Generate URL B from the same document, adding A's status to `override_fields`. Verify that the supplied field values are identical between URLs and only the explicit override list changes. BadgeApp's documented status-override behavior should now replace A's status and paired justification. Open the exact returned URL through a second delivery route, by copying the complete raw URL directly into Chrome's address bar; compare the copied string with `artifact.url` rather than reconstructing it from visible text. Compare the remaining fields again. Each URL starts from the site's saved baseline; do not save between cases. Record any automation notice separately from the proposed changes.

## Completion

Record each case as passed, failed or unexercised, with brief actual-versus-expected notes and screenshots of the baseline and both previews. Discard the previews by opening the plain edit page, and capture the restored controls for each selected case. Confirm their statuses and displayed text match the baseline and that QA text is gone. Identify hidden or uninspected values explicitly. A subsequent `get_project_progress` read should match the earlier saved answers; it supplements rather than replaces the browser restoration check. Retain both exact proposal URLs alongside their tool results. Confirm that no Save/Submit action was performed. The result qualifies the tested candidate, PolicyChecks silver, selected conditions and delivery paths; it does not establish all-level coverage or saved-state behavior. Resolve failures before stable promotion and rerun affected cases after a candidate change.
