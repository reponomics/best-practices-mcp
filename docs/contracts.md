# V1 implementation contract

The [specification](specification.md) defines scope and tool inputs; this document defines exact result payloads, operational policies and edge cases for the implemented ten-tool server. Compatibility discrepancies require review before changing the contract.

## Common conventions

Use snake_case domain properties and strict JSON types. Objects below list their required properties; nullable properties are present as `null`. Reject extra tool arguments. SDK-generated input/output JSON Schemas are implementation deliverables, generated from these definitions and checked by fixtures. Do not introduce a second handwritten protocol implementation. Successful `get_criteria`, `get_project_progress`, `validate_draft` and `prepare_update_url` payloads use `schema_version: 2`; all other successful payloads and every error payload use `schema_version: 1`; JSON text content carries the same payload for clients without structured-content support. SDK wire names remain unchanged.

`project_id` is an integer greater than zero; storage uses its decimal representation. The published schema declares an integer. At the tool boundary the server also accepts an integer-valued number (`123.0`) or an ASCII decimal string (`"123"`) for `project_id` and `page`, and converts it. Booleans, fractions, signs, whitespace and other strings remain invalid. `level` is one of `passing`, `silver`, `gold`, `baseline-1`, `baseline-2`, `baseline-3`. `criterion_ids`, when supplied, is an array of distinct canonical IDs; `[]` selects none, omission selects all, and a filter without a level is invalid. Unknown IDs for the selected level are errors, including an ID valid only at another level. Arrays of result fields/criteria use canonical lexical order, except project candidates, which preserve upstream order. No selection is inferred from the first search result.

Optional arguments may be omitted. A `null` optional argument is treated as omitted, and a `null` required argument is reported as missing; the published schemas keep the canonical form without `null`. `draft` is the exception: omission selects the stored draft, so `draft: null` is rejected with a message naming the two valid choices. Use a distinct internal omission sentinel for `draft`; do not implement omission as `draft or read_file()`. `{}` is a valid explicit draft. `changes` is a JSON object; null is allowed only as a property value indicating removal. `build_draft` defaults `changes` to `{}`; `update_draft` requires it. An empty update to an absent draft creates `{}` as an explicit write. Empty updates to an existing valid draft need not rewrite it.

`Draft` is a flat map with string keys and JSON values. Published arbitrary-JSON fields explicitly enumerate null, Boolean, number, string, array and object with `anyOf`; collection children remain arbitrary JSON. This is schema-description guidance, not an object-only restriction or a change to runtime validation. See the [schema compatibility](schema-compatibility.md). Preserve unfamiliar JSON values, including nested objects/arrays, without interpreting them. Reject non-finite numbers, invalid Unicode, duplicate JSON keys in file/import bytes, non-object roots, and alias conflicts. MCP has already decoded tool input; the server cannot promise to detect duplicate keys erased by the protocol decoder. Aliases and canonical fields with identical values collapse to one canonical field; different values are `invalid_document`. Do not infer aliases by punctuation or case. Normalize against the pinned catalog alias map only.

Recognized status and justification fields and the four metadata fields are writable. All non-null patch assignments to unfamiliar or provenance fields (`id`, `repo_url`) fail, even if the field already exists. Null can remove any named field, including an absent or unfamiliar one. Conflicting aliases inside a patch fail before mutation; normalize the base and patch separately, then apply canonical keys. Thus a patch through an alias can intentionally replace a base canonical value. A recognized invalid base value can be repaired by a patch before structural validation. Invalid JSON or conflicting aliases cannot be repaired through a patch.

## Shared result types

| Type | Required properties and meaning |
| --- | --- |
| `CatalogRef` | `revision: string` (full upstream commit), `source_url: string`, `generated_at: string` (UTC RFC3339), `format_version: 1`. |
| `Observation` | `project_id: integer`, `source_url: string` (actual public JSON request), `fetched_at: string` (UTC RFC3339 after successful body receipt), `attribution: string|null`, `license: string|null` (upstream project-entry fields). |
| `Project` | `project_id: integer`, `name: string|null`, `repo_url: string|null`, `homepage_url: string|null`; absence is null here, never an invented answer. |
| `BadgeObservation` | `source_url: string`, `fetched_at: string`, `service_attribution: string`, `project_entry_attribution: null`, `project_entry_license: null`. Badge endpoints do not supply record attribution/license; service credit is identified separately, with no extra full-record fetch. |
| `DraftSource` | `kind: "explicit"|"stored"`, `location: string|null`; absolute server path only for stored source. |
| `StructuralIssue` | `field: string`, `code: "unknown_field"|"invalid_type"|"invalid_status"`, `message: string`; diagnostics never include a copy of the field value. The `invalid_status` message lists the four accepted status strings. |
| `Identity` | `association: "storage_key"|"document_provenance"|"explicit_target"`, `id_check: "matched"|"absent"`, `repo_check: "matched"|"absent"|"not_checked"`. Storage-key association takes precedence, then explicit-document provenance, then caller target. This is association, not authentication. |
| `Error` | `code: string`, `message: string`, `details: object` (field/path/ID/status/limit as applicable, no answer bodies), `recovery: string`, `retry_after_seconds: integer|null`. |

Application failures return `{schema_version: 1, error: Error}` in an SDK `CallToolResult` with `isError: true`, structured content, and equivalent JSON text. Expected failures are translated at the tool boundary rather than thrown as generic SDK exceptions that lose the code. Rejected tool arguments are such a failure: they return `invalid_arguments` with `details.issues`, one entry per argument in name order. Each entry has `field` and `problem`, plus `allowed` (the accepted values) for an enumerated argument or `expected` (the argument's description) when a nested shape does not match. Issues never repeat a supplied value; an unrecognized argument name is reported truncated to 64 characters. Invalid protocol messages and unknown tool names remain SDK-owned protocol errors. Each advertised output schema uses JSON Schema 2020-12 anyOf to include the tool-specific success payload and the shared error payload; both structured result variants must conform. The wire isError flag distinguishes tool failures independently of that schema. Validate both domain variants in contract tests, even if the SDK skips output validation for isError results. Unexpected exceptions return `internal_error`, a generic message, and no traceback/body to the client.

Stable domain codes: `invalid_arguments`, `invalid_document`, `invalid_field`, `invalid_level`, `invalid_criterion`, `invalid_category`, `invalid_query`, `invalid_override`, `draft_not_found`, `draft_read_failed`, `draft_write_failed`, `document_too_large`, `response_too_large`, `project_not_found`, `project_mismatch`, `project_identity_unresolved`, `upstream_unavailable`, `upstream_invalid_response`, `rate_limited`, `internal_error`. Recoveries identify an actual next action, such as supplying an explicit document, fixing a field, retrying a public read later, or reading after an uncertain write. There are no revision/conflict or validation-bypass tokens.

## Ten success payloads

All rows also contain `schema_version`, using version 2 for the catalog read, the progress read, validation and proposal preparation, and version 1 otherwise. Input signatures are defined in [specification section 4](specification.md#4-tool-surface).

No level gives all six summaries, `detail: null` and an empty criteria array; a level gives only its own summary. `CriterionSummary` (index detail) has `criterion_id`, `category: string|null`, `requirement: string|null` (upstream MUST/SHOULD/SUGGESTED category). `Criterion` (full detail) has `criterion_id`, `level`, `description`, `details: string|null`, `category`, `requirement`, `status_field`, `justification_field`, `aliases: string[]`, `na_allowed: boolean`, `na_justification_required: boolean`, `met_justification_required: boolean`, `met_url_required: boolean`. For passing, silver and gold, `category` is the upstream major group. Baseline YAML files every control under one group, so a Baseline `category` is the documented name of the two-letter code in the criterion ID (`osps_ac_…` is Access Control). Official text is retained, not rewritten by a model. |
| `find_project` | `query: string`, `query_kind: "id"|"url"|"text"`, `page: integer`, `candidates: Candidate[]`, `next_page: integer|null`, `pagination_complete: boolean`, `observation: {source_url, fetched_at}`. `Candidate` contains `project: Project`, `match_basis: "id"|"repo_url"|"homepage_url"|"url_query"|"text"`. |
| `get_project_progress` | `project: Project`, `level: Level|null`, `summaries: Summary[]`, `answers: Draft`, `criterion_ids: string[]`, `level_criterion_count: integer|null`, `observation: Observation`, `catalog: CatalogRef`, `summary_metadata: object` containing only present upstream badge_level, tiered_percentage, baseline_tiered_percentage values. `Summary` has `level`, `upstream_percentage: number|null`; no local percentage substitutes for a missing one. `criterion_ids` lists the criteria that matched every filter, including those with nothing saved; `level_criterion_count` is the size of the selected level. A field is in `answers` exactly when the public record supplies it, so presence of the key replaces a separate presence flag and a supplied `null` stays `null`. No level returns summaries/metadata with empty `answers` and `criterion_ids` and a null count. A level returns the supplied canonical fields of the matching criteria, preserving unexpected upstream field values for diagnostics, never synthesizing `?`. |
| `get_project_badge_status` | `project: {project_id, name: string|null}`, `family: "best_practices"|"baseline"`, `badge_level: string|null`, `badge_state: "earned"|"in_progress"|"unrecognized"|"unknown"`, `progress: {field: "tiered_percentage"|"badge_percentage", value: number|null, level: "baseline-1"|null}`, `updated_at: string|null`, `updated_at_status: "valid"|"missing"|"invalid"`, `observation: BadgeObservation`, `caveats: string[]`. |
| `get_project_badge_svg` | `project_id`, `family: "best_practices"|"baseline"`, `image_url: string`, `project_url: string`, `markdown: string`, `artifact: {svg: string, media_type: "image/svg+xml", suggested_filename: string, encoded_size_bytes: integer}`, `observation: BadgeObservation`, `caveats: string[]`. `artifact.svg` preserves the decoded upstream SVG text; its byte count is UTF-8 content size. |
| `build_draft` | `draft: Draft`, `issues: StructuralIssue[]`, `serialized_size_bytes: integer`. Only unknown-field warnings can remain after a successful mutation. |
| `read_draft` | `project_id`, `draft: Draft`, `location: string`, `issues: StructuralIssue[]`, `serialized_size_bytes: integer`, `identity: Identity`. Recognized invalid values remain visible with diagnostics. |
| `update_draft` | `project_id`, `applied_patch: object`, `created: boolean`, `location: string`, `issues: StructuralIssue[]`, `serialized_size_bytes: integer`, `identity: Identity`. Applied patch is the normalized accepted request, including null removals and content no-ops; no full document echo. |
| `validate_draft` | `project_id`, `section`, `draft_source: DraftSource`, `identity: Identity`, `catalog: CatalogRef`, `findings: Finding[]`, `checked_criteria: {level, criterion_id}[]`, `skipped_criteria: Skipped[]`, `warnings: CompatibilityWarning[]`. `Finding` has `level: Level|null`, `criterion_id: string|null`, `field`, `code`, `requirement: string`, `message`. `Skipped` has `level`, `criterion_id`, `reason: "status_absent"|"status_unknown"|"status_invalid"|"other_level"`, `checks: string[]`. |
| `prepare_update_url` | Common artifact result below, plus normalized `overrides: Overrides`, `effective_overrides: string[]`; `artifact` is `{url: string, encoded_size_bytes: integer}` or null. |

`validate_draft` checks only supplied criteria in the selected section; `choose_section` checks them independently at each applicable level. Wholly absent criteria appear in neither scope array. A criterion with a supplied field appears in checked scope for shape checks and may also appear in skipped scope for conditional checks; these arrays are not disjoint. Unknown fields receive `unknown_field` findings with null level and criterion ID. For a specific section, fields belonging only to other levels receive level-qualified skipped entries. Metadata shape findings also use null level and criterion ID. Supported finding codes are `invalid_type`, `invalid_status`, `unknown_field`, `na_not_allowed`, `missing_required_justification`, `missing_required_url`. Invalid and unknown statuses skip conditional checks. `Unmet` has no conditional evidence requirement. The exact five-character/comment-prefix/URL predicates remain those in spec section 4.

The populated criterion booleans express upstream requirements, including implied requirements. Upstream deliberately permits omitting an entailed YAML field: `met_url_required` implies `met_justification_required`, and `na_justification_required` implies `na_allowed`. Catalog generation expands those implications before publishing explicit values; omission of an entailed field is not absence of the requirement. The original YAML remains unchanged as provenance. For example, gold `build_reproducible` publishes both Met flags as true. These are mechanical upstream conventions, not host policy or predictions about saved form values.

For a Met answer requiring a URL, validation reports `missing_required_url` without also reporting the entailed `missing_required_justification`. A matching URL satisfies both existing predicates. This follows upstream's stronger-first checks and retains the accepted answer set; standalone justification and N/A checks retain their existing predicates.

## Read selection and migration

`get_criteria` accepts `level`, `criterion_ids`, `category` and `detail`. `criterion_ids`, `category` and `detail` each require `level`, and `category` cannot be combined with `criterion_ids`. `category` is one of the level's `categories`, matched exactly; any other value is `invalid_category` with the allowed names in `details.allowed`. `detail` defaults to `full` when `criterion_ids` is supplied (including `[]`) and to `index` otherwise. The default index keeps a whole-level listing small.

`get_project_progress` accepts `level`, `criterion_ids`, `statuses` and `include_justifications` (default true). `statuses` requires `level`, holds distinct values from `Met`, `Unmet`, `N/A`, `?` and `absent`, and combines with `criterion_ids` by intersection; `[]` selects none. `absent` selects criteria whose status field is missing from the public record. A saved status outside the four known strings, including `null`, matches no status filter and is returned only when `statuses` is omitted. With `include_justifications: false`, `answers` holds status fields only.

Callers of the version 1 results should request `detail: "full"` for whole-level definitions, read the constant text source from `catalog.text_source_url` rather than each criterion's `source_url`, take level names from `levels[].level`, and read saved values and their presence from `answers` rather than the removed `criteria` list. Error payloads remain version 1.

## Proposal interface migration

For `validate_draft` and `prepare_update_url`, replace `level` with required `section`: a supported level or `choose_section`. The latter deliberately defers section selection and produces `/choose/edit`. Replace `override_fields` with `overrides: {"mode":"fields","fields":[...]}`, or select `none`/`all`. Read the normalized `overrides` result instead of `requested_overrides`, level-qualified validation scope, transfer applicability/restrictions, and `warnings`. These tools return success schema version 2; their shared errors remain version 1. Other tools retain their existing `level` inputs and version 1 payloads.

## Badge observations and SVG artifacts

The status tool defaults an omitted or null `family` to `best_practices`; the SVG tool requires an explicit family. Both reject unsupported families. Each call fetches only its requested representation and one family. Badge JSON must be an object with a strict positive ID matching the requested project; a different ID is `project_mismatch`. No full-record request fills missing metadata. The SVG endpoint supplies no project name; its artifact and links identify the requested project ID and family.

Status preserves the raw `badge_level`. Recognized Best Practices values are `in_progress`, `passing`, `silver` and `gold`; recognized Baseline values are `baseline-1`, `baseline-2`, `baseline-3` and `baseline-pct-N` for integers 0 through 99. Earned levels map to `badge_state: "earned"`; in-progress values map to `"in_progress"`; a missing/null value maps to `"unknown"`; other strings remain visible with `"unrecognized"`. Unexpected non-string field values fail `upstream_invalid_response` rather than being coerced into badge states.

For Best Practices, `progress.field` is `tiered_percentage` and `progress.level` is null. For Baseline, the field is `badge_percentage` and the level is explicitly `baseline-1`. Missing/null progress is null; finite upstream numbers remain unchanged. Booleans and nonnumeric values are invalid responses. The compact Baseline percentage is not progress toward level 2 or 3; those questions require `get_project_progress`.

The raw `updated_at` string is retained. A valid timezone-bearing RFC3339 timestamp has `updated_at_status: "valid"`; an absent/null value has `"missing"`; malformed timestamp text has `"invalid"`. Non-string timestamps fail as invalid upstream responses. Never replace this value with `fetched_at`. Both badge families expose the project-record timestamp. No relative freshness ordering between compact badge JSON and full project JSON has been established. Saved-field comparisons use `get_project_progress` because it supplies the criterion answers; the compact response supplies summary fields. No status preflight is required.

SVG requests use explicit `.svg` routes, require `image/svg+xml`, and accept only well-formed UTF-8 XML with a root in the SVG namespace. DTD/entity declarations are rejected. This validation does not sanitize SVG or make it safe for arbitrary execution; the server returns it as inert text in the structured result and equivalent JSON text fallback, never as rendered image content. The Markdown snippet uses the dynamic project badge URL rather than a static status image. Saving the SVG or inserting the snippet is the host's action.

## Identity and source decisions

Check a present `id` as a strict positive integer equal to the requested target. Wrong type is `project_identity_unresolved`; a different valid ID is `project_mismatch`. For stored reads/updates, check source identity before patching; a patch cannot silently repurpose another project's file. Recovery is explicit host/user repair of the misplaced file, or a corrected explicit document for document mode. `build_draft` has no target and only preserves/removes provenance. Validation with explicit/stored input checks `id` but does not check `repo_url` against the network (`repo_check: "not_checked"`).

Generators check any supplied `repo_url` against the fetched project. Both URLs must be absolute HTTP(S), have a host, and contain no credentials. Compare after lowercasing scheme/host and removing the scheme's default port; preserve scheme differences, path case, trailing slash, query, fragment, and percent encoding. Do not drop `.git`, follow redirects, fetch the URL, or equate providers. Identical normalized values match. Different comparable values are `project_mismatch`; missing/unusable upstream provenance when a draft URL is supplied is `project_identity_unresolved`. Both prevent artifacts. Absent draft provenance is allowed and honestly reported as explicit targeting or storage association. No additional host registration state is stored.

## Transfer report and aggregation

Common artifact result: `project_id`, `section`, `catalog`, `draft_source`, `observation`, `identity`, `warnings: CompatibilityWarning[]`, `outcome`, `artifact`, `no_artifact_reason: string|null`, `transfer: TransferField[]`. One row per supplied normalized field, including provenance and fields outside the selected level. `TransferField` contains `field`, `disposition: "encoded"|"outside_level"|"unsupported"|"invalid"|"omitted"`, `reason: string`, `override: boolean`, `applicable_levels: Level[]`, and `restrictions: {level, reason}[]`. Chooser proposals retain values allowed at any applicable level and report restrictions elsewhere. Do not repeat answer bodies in the report. The report describes artifact inclusion and exclusions, not expected form effects. Observation metadata records the public read used to verify the registered target and supplied identity. Saved answers are not used to select or omit proposals.

Every eligible supplied field is encoded, including values equal to the observed answer, empty strings, whitespace and control characters. Values remain exact strings: the generator does not trim them or reproduce BadgeApp normalization. Classify artifact outcomes in this order:

1. Any encoded fields plus any requested unsupported/invalid/omitted fields yields `partial`.
2. Any encoded fields with none of those omissions yields `complete`.
3. No encoded fields and any unsupported/invalid/omitted requested fields yields `no_transferable_changes` and artifact=null.
4. Otherwise, `no_supplied_transferable_answers` and artifact=null (empty document, provenance-only, or other-level-only).

Unknown fields are unsupported; provenance rows are omitted with reason `provenance_not_editable` and excluded from requested-work aggregation. Other-level fields are also excluded from aggregation. Status `?` is encoded with a compatibility warning; its valid supplied justification is evaluated independently. An invalid in-scope status or `N/A` unsupported at every selected applicable level causes its accompanying supplied justification to be omitted with `invalid_companion_status`. A justification of invalid type does not disqualify an otherwise valid supplied status. No missing justification or evidence-URL check runs during generation.

## Artifacts and overrides

`Overrides` is `{"mode":"none"}` (default), `{"mode":"all"}`, or `{"mode":"fields","fields":[...]}`. Only `fields` accepts a nonempty field list: deduplicated, sorted exact canonical names, supplied and writable in scope. Reject aliases, globs and unknown/provenance/out-of-scope/unsupplied names; callers express wildcard intent through `all`. Reject extra or contradictory properties and null. The result echoes normalized `overrides`; `effective_overrides` lists encoded fields covered by the mode. `all` encodes the wildcard and covers only supplied eligible proposals. A transfer row’s `override` is true exactly when its field is in that list, without predicting replacement. For selected fields, do not expand a status override into a justification override; preserve supplied pairs so BadgeApp applies its documented implication.

`CompatibilityWarning` contains `code: "unknown_status_reset_unsupported"`, sorted affected `fields: string[]`, `message`, and `observed_on`. Both tools return the shared nonblocking warning for in-scope `?` answers: resetting through a URL is observed not to work even with overrides, despite conflicting BadgeApp documentation. This does not invalidate an unknown draft answer or claim reset intent. The warning reports the limitation without recommending an alternative update method. No live probe or bypass flag is required.

No-artifact reason equals the outcome enum, accompanied by field reasons in the transfer report. A valid empty search, completed validation with findings, and null artifact all remain successful tool results. URL generation does not promise the state of the rendered or saved form.

## Resource and network policy

These are server resource limits, not BadgeApp field or URL transport limits. Initial constants are 1,048,576 bytes per normalized draft or patch, 16,777,216 bytes per serialized SDK tool-result object (including structured and compatibility text representations), 8,388,608 decompressed bytes per upstream JSON response, and 1,048,576 decompressed bytes per upstream SVG response. Draft/file input is additionally bounded at 1,048,576 raw UTF-8 bytes before parsing. Maximum JSON nesting is 64. Serialization for draft size and file bytes uses UTF-8, ensure_ascii=false, sorted keys, compact separators, no non-finite values, and one final newline. Tool-result measurement uses the pinned SDK's actual wire serialization, excluding the JSON-RPC ID/frame. The final result budget still applies to SVG after JSON escaping and duplication into structured/text channels. A host may impose a smaller limit; qualify it at release rather than claiming universal capacity.

Before replacement, serialize both the candidate document and the complete prospective read result, including diagnostics, absolute location, identity, and text fallback; require both budgets to pass. A no-op update also performs these checks. Incoming oversized stored/imported files fail explicitly; they are never truncated. Large criteria/progress/search results fail `response_too_large` with filter/page guidance. An artifact that exceeds the response budget fails explicitly, not with a partial URL or guessed URL-length threshold. Boundary fixtures must include Unicode, escaping, unknown-field diagnostics, and long storage paths; exact envelope accounting is required even with generous headroom.

Use one lifespan-managed asynchronous HTTP client, no cookies/authentication, fixed production origin, and a descriptive User-Agent containing package/version. Do not follow redirects; return `upstream_invalid_response` for unexpected redirect, wrong media type, malformed SVG or HTML login/error content. Never fetch candidate/evidence/repository URLs. Send only documented query parameters; badge JSON/SVG routes take none. Share a monotonic limiter across JSON/SVG calls and retries: at most one request start per second per process. No cache of project observations across calls.

Each read has at most three attempts and a 30-second overall deadline, including limiter wait, backoff, and body reads. Each attempt has a 10-second timeout, with connection timeout at most 5 seconds. Retry only transient connection/read failures and HTTP 429/502/503/504; delays after attempts one/two are at least 1/2 seconds, also subject to pacing. Parse Retry-After as nonnegative seconds or HTTP date; apply its delay as a shared cooldown. If the cooldown exceeds the remaining deadline, return immediately with rate_limited and retry_after_seconds rather than sleeping past the budget. Never shorten a valid cooldown; malformed values use normal backoff. HTTP 404 maps to project_not_found on a single-project read and empty candidates for ID discovery; other unexpected HTTP/schema failures do not retry. Cancellation stops pending reads/waits and releases resources. HTTP errors do not expose response bodies.

## Storage and protocol adaptation

Resolve defaults without creating them: macOS `~/Library/Application Support/bestpractices-mcp`; Linux `$XDG_DATA_HOME/bestpractices-mcp` when absolute, otherwise `~/.local/share/bestpractices-mcp`; Windows `%LOCALAPPDATA%/bestpractices-mcp`. Empty/relative BESTPRACTICES_DATA_DIR is startup configuration error. An existing override must be a directory; missing absolute roots are allowed. Do not expand `~` in an override. Reject symlinks in server-managed `projects`, project directory, and draft destination, and non-regular draft files. Resolve the configured root once; a user-chosen root may itself resolve through a symlink. Protect against accidental path escape; hostile concurrent replacement of ancestor directories by another local user is outside the single-writer local-storage guarantee.

Use a process-local per-project async guard, a same-directory temporary file, owner-only creation permissions where supported, preserved destination permissions, flush plus file fsync, then atomic replacement. Clean temporary files on handled pre-replacement failure; cancellation must not strand a held guard. Shield the bounded replace/cleanup critical section so cancellation cannot trigger a retry of a possibly committed write. Atomic visibility is promised; survival of sudden hardware/power failure is not. Never claim rollback after replacement. Empty directories left by a failed first update may remain; no successful draft is claimed.

Use SDK annotations: readOnlyHint=true for all but update_draft; update_draft has readOnlyHint=false and destructiveHint=true because it can replace/remove local fields. idempotentHint=true for deterministic local document/catalog operations and update_draft's content semantics; document that this does not authorize retries after ambiguous writes. Both badge tools also have idempotentHint=true: repeated reads add no side effects, but may observe different values. Existing public-read/generator annotations remain unchanged. openWorldHint=true only for network tools, including both badge tools. Discovery/list caching uses SDK CacheHint(ttl_ms=0, scope="public"); no application-result caching is promised. Keep handlers small; services return domain objects and the MCP boundary performs schema/error/size adaptation.

## Required contract examples

Regression fixtures cover these cases.

- `build_draft({},{"description_good_status":"Met"})` returns that single-field document; optional validation may find a missing explanation, while generation still proposes Met.
- `build_draft({"extra":{"x":1}}, {})` preserves extra with unknown_field diagnostic; setting extra non-null fails; removing extra with null succeeds.
- `read_draft(123)` missing returns draft_not_found and creates nothing. `update_draft(123,{})` creates an empty draft. A repeated empty update has created=false.
- `validate_draft(123,"passing",{})` checks no criteria and performs no file or network access. `draft:null` fails with `invalid_arguments`, as does an omitted `section`.
- `get_criteria(level="bronze")` returns `invalid_arguments` whose `level` issue lists the six levels. `get_criteria(criterion_ids=[...])` without a level reports `criterion_ids` with problem `requires level`.
- An omitted draft loads the stored file; explicit `{}` ignores even a malformed stored file. A mismatched stored id fails read/update before mutation.
- Supplied Met with a justification and an override on the status encodes both fields and only the explicit status override, including when either or both values match the public record.
- Supplied Met plus text with only the justification overridden preserves both supplied values and that exact override. The report identifies included fields without classifying upstream retention or coupling effects.
- Unknown-only input yields an artifact with a compatibility warning; other-level-only input yields no_supplied_transferable_answers; eligible fields matching the public record yield complete; matching eligible fields plus unsupported work yield partial.
